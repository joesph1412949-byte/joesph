### 3.2 差异逐条解释

1. **交易笔数 1068 → 0(full_factor_v1)**: 默认口径下 `gate_blocked_days=21/254`(门控只在 21 天拦人),
   旧口径下 `gate_blocked_days=254/254`(天天拦)。原因: N6(美股映射)/N7(美债)/N8(VIX) 依赖市场数据层缓存,
   N3/N4/N5 依赖逐日 em/ticks 快照, 不注入则恒 0; 8 项门控只剩 N1/N2 能命中(2 < threshold 3)→ **门控永不达标**
   → `candidates=0`。报告的 `gate_notes` 已如实点名: `["N3 缺em+ticks数据 → 0", "N4 缺em数据 → 0", "N5 缺ticks数据 → 0"]`。
2. **28 个评分因子从"25 命中"变成"0 个被评估"**: 门控永不过 → 一只候选都没算过。这正是"残废版策略"的指纹,
   也正是本次 `factor_hits` 要暴露的东西: 旧口径下 28 个评分因子的 `status` 全是**未评估**(不是"恒 0"),
   说明问题出在**数据供给/门控**, 而不是因子本身算不出来 —— 两者在报告里第一次可以区分。
3. **v04: 9 个评分因子从 9/9 命中变成只有 F5 命中(其余 8 个恒 0)**。v04 门控只有 N1, 而 N1 在无 day_feed 时
   走兜底分支 `1 if len(limit_ups) > 0 else 0` —— 池非空日恒 1 → **命中率 100.00%(常数)**,
   门控等于没有(`gate_blocked_days=0`)。于是 17,386 只候选全部进入评分, 但 F1/F2/F4/F6/F7/F8/F9 需要
   逐日快照/市场数据/1m 特征/基本面 → 恒 0, 模型分上限 1 < `candidate_min_model=3` → `filtered_min_model=17386`
   (**全部被过滤**)→ 0 笔。F5 只靠 K 线成交量就能算, 所以它是旧口径下唯一"活着"的评分因子。
4. **旧口径下 N1 是常数因子**: 这是本次新增的"rate==1.0 标注"抓到的第一个真问题 ——
   一个恒定命中的门控因子对筛选毫无贡献, 却在旧报告里看不出来(旧报告只有 `gate_notes` 的"缺数据"提示)。
5. **交易成本口径一致**: 四份报告 `cost_config` 都是 `fee_rate=0.00025 / min_commission=5.0 / slippage=0.001 /
   stamp_duty=0.0005 / transfer_fee=0.00001`, 平均成本 0.103%/笔(含 Task 4 的 ¥5 最低佣金双腿下限差额),
   新旧对比**不是靠成本差异**造出来的。
6. **默认口径下 F7/Y6/Y7 命中率极低(0.47% / 0.34% / 2.23%)是基本面缓存覆盖所致**: `data_notes` 写明
   "F7/Y6/Y7 覆盖 24/254 天" —— 回测默认只读基本面缓存不联网(用户 2026-09-17 拍板), 未采集的日子 fail-open 0。
   **这三个因子的命中率目前不可用于评估其有效性**, 只说明"缓存覆盖到哪"。补数据:
   `python -m prism.fund_snapshot --date YYYYMMDD`。

```
=== full_factor_v1 2025-09-01~2026-09-16: S2 子条件分布(候选评估 16341 次) ===
  kline 不足 60 根        : 183
  有 60 根K线             : 16341
  volume 全 1.0(契约塌陷) : 0          ← 成交量是真实值, 不是旧 2 元组塌陷
  ≥20 天放量(>1.5×均值)   : 76         ← 条件 A 能成立(最多 28 天)
  60 日振幅 <=10%         : 1          ← 条件 B 几乎不成立
  两者同时满足(S2 命中)   : 0
```

S2 = "60 日 ≥20 天放量 **且** 价格窄幅震荡(振幅 ≤10%)"。候选池全是**当日涨停股**:
刚涨停的票 60 日振幅天然偏大(16,341 次里只有 1 次 ≤10%), 而那 1 次振幅达标的样本放量天数只有 6 天。
两个子条件在"涨停股"这个候选宇宙里几乎互斥 → **S2 在本窗口 0 命中是策略定义与市场事实的结果, 不是算不出来**。
(S2 的定义是否需要调整属策略问题, 不在 Task 5 范围, 未改。)

### 7.4 环境异常(00:21 之后 QMT 离线) —— 影响复跑, 不影响本报告结论

- **观察**: 00:18–00:21 的四次全窗口回测正常(§7.2)。之后 QMT(miniQMT/xtdata)**掉线**:
  实测 `xtdata.connect()` 与 `xtdata.get_local_data(...)` 均抛
  `Exception('无法连接xtquant服务，请检查QMT-投研版或QMT-极简版是否开启')`, **每次调用耗时 ~2.04 s(连接超时)**。
  14:14 起同一条命令 `... --strategy first_board_v04 --no-market-data` **跑 600 秒无输出被超时杀掉**,
  5 天窗口(20260901–20260905)300 秒也未完成(此前同命令 7 秒)。
- **根因(实测)**: 逐层计时里 `qmt_kline_feed(code)` = 2.0–2.4 s/只, **那 ~2.0 s 就是 xtdata 的连接超时**;
  数据其实来自 `qmt_kline_feed` 第二档兜底(zt_history 缓存, 413 根), 缓存未命中时才落到东财/腾讯网络回退(更慢)。
  8 线程并发无加速(5 日池 185 只 wall 377.8 s ⇒ ~2 s/只), 全窗口 2500+ 只 ⇒ 预计 1.5–3 小时。
  (`import backtest.cli` 1.1 s / `zt_feed` 0.5 s / `load_market_data` 0.1 s 均正常。)
  *更正说明: 本节初稿写成"QMT 本地读盘退化", 在控制者指出 QMT 离线后实测 `connect()` 抛异常, 已更正为"QMT 离线"。*
- **判定**: 纯环境问题, 与本任务代码无关(改动只在报告统计字段与说明文案, 不触碰取数路径)。
  **反证**: 四份 JSON 来自 QMT 在线时(63–82 s 跑完 254 日全窗口 ⇒ 本地读是毫秒级), 不是网络回退跑出来的。
- **处置**: **14:14 与 14:39 两次复跑均中止, 未采用**。用最终代码复跑 3 份口径并逐字节比对首批 JSON:
  `full_factor_v1 默认`(662,314 B)、`full_factor_v1 --no-market-data`(5,538 B)、`first_board_v04 默认`(474,873 B)
  全部 `identical=True` ⇒ 最终代码与首批代码在这些策略上行为完全一致。第 4 份(`t5-v04-nomkt`)的数字**同样不受
  最终代码差异影响**: 该差异仅为"策略未用到 F3 时不写代理说明"这一条守卫, 而该口径没有 day_feed → 无 1m 注入 →
  `_proxy_seen` 为空 → 那条说明本就不会产生(该 run 的 `data_notes` 实测为空)。
  需要逐字复跑确认时(等 QMT 恢复后):
  `python -m backtest.cli --start 20250901 --end 20260916 --strategy first_board_v04 --no-market-data`
