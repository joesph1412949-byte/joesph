# 模拟盘打板成交升级 —— 排板队列状态机 设计规格

日期：2026-09-02 ｜ 状态：已获用户批准（方案 B：直接上排队状态机）
上游：模拟盘（paper.py/paper_daemon.py，终审已闭环）、编辑器默认指针（engine.active_strategy_id 热重载）
参考：limit-up-sniper（A 股首板打板开源系统）排队成交模型 + A 股撮合物理

## 1. 目标与动因

当前模拟盘买入"开过板即全量成交"，是已披露的最大乐观偏差（真实打板要排队，多数排不到）。本升级把买入从"立即成交"改为**排板队列状态机**：排队是否成交由真实盘口数据验证（涨停价新增成交量穿越队列），开板/收盘未成交即撤单。偏差方向从乐观转保守，模拟结果更接近真实打板客的世界。

配套同步修正两处乐观假设：
- 排队成交价 = 涨停价**挂单价**（无 +0.1% 上滑——那是扫板抢筹的代价，排板排队不该付）
- 跌停日卖出不再按触发价全成交，改为当日卖不出、顺延次日再卖

## 2. 排板状态机

### 2.1 买入路径改造

三时点选股后，候选通过既有五关（未持仓/现金够/仓位未满/非一字板/金额够一手）后：
- 创建 **pending_buy 排板委托**（不再立即记账成交）
- 前置板质量检查（不通过则不创建委托，记 skips）：
  1. **封单金额门槛**：买一量 × 涨停价 ≥ 2000 万（封单薄的板排队也是等炸）
  2. **尾盘不排**：候选首次触板时间 < 14:30（14:30 后才首触板的尾板次日溢价差）
- 换手率过滤**不加**（选股维度由 F 系因子管，执行层保持纯排队物理）

### 2.2 委托数据结构（账本新键 `pending_buys`，数组）

每项：
```json
{"code": "600000", "shares": 300, "price": 10.11, "amount": 3033.0,
 "queued_shares": 120000, "base_volume": 15678900,
 "created": "2026-09-02T10:00:05", "slot": "T10:00",
 "frozen": 3033.0}
```
- `price`：委托时涨停价（成交价固定此值，排队不吃滑点）
- `shares`：手数取整后的股数；`amount`：委托金额（含费预估——冻结用）
- `queued_shares`：委托时刻**买一量（封单手数）**——前方队列
- `base_volume`：委托时刻该股**当日累计成交量**（手）
- `frozen`：冻结现金额（成交前从可用现金剔除）

### 2.3 每轮（5 秒）检查：三结局

守护每轮对所有 pending_buy 拉最新盘口（`get_full_tick`：last/volume/bid1/bidVol1/ask1），逐一判定：

1. **成交**：`当日累计量 - base_volume ≥ queued_shares + shares` **且当前仍封板**（last == 涨停价）→ 整单按 `price` 成交：
   - 扣现金 = 成交金额 + 买入费用（佣金万2.5+过户费万0.1，按成交金额，与既有 buy 记账一致）
   - 记 trades 流水（reason="queue_fill"）、进 holdings（buy_date=今日，T+1 生效）
   - 解冻剩余（frozen - 实扣金额）：成交金额按 shares×price 实算（手数取整后 ≤ 冻结额，差额解冻回现金）
   - 移除 pending
2. **开板撤单**：当前 last < 涨停价 → 排队位置永久失效，撤单：解冻现金、记一笔**未成交流水**（trades 增 `{"reason": "queue_cancel_break", "side": "buy", "code", "shares", "price", "ts"}` —— 便于网页展示"几次排队失败"），当日不再为该 code 建新排板委托（当日幂等键 `canceled_pending_codes` 记 code——下一时点若再选中可重新排板？不行，当日同一码撤单后再封也不排——limit-up-sniper 是开板后失效当日不再追。保持一致：**当日不再为该 code 排板**，记录键）
3. **收盘失效**：15:00 结算时仍有 pending 未成交 → 撤单解冻、记未成交流水（reason="queue_expire"），`pending_buys` 清空（防跨日残留悬单）

**封单减少不算成交**（可能只是别人撤单——成交只认"新增成交量穿越队列"这唯一硬证据）。

### 2.4 幂等与安全（沿用模拟盘既有纪律）

- pending 创建/成交/撤单全部走临界段：`_snapshot_state()` → 改 → `save()`（原子写）→ 失败回滚；**保存成功才算事件发生**
- 重复委托防护：pending 存在期间该 code 不重复建委托（含跨时点）
- `_buyable` 的"今日已交易"检查扩展为"今日已成交 ∨ 今日有 pending ∨ 今日已撤单(code)"三重口径——成交/撤单各自的当日幂等键分离，防止撤单后下一时点无限重排
- 断电崩溃：pending 在账本里，重启恢复继续盯；跨日启动时旧 pending 按收盘失效清理

## 3. 资金冻结语义

`available_cash = cash - Σ(pending.frozen)`：
- 创建委托时校验 `available_cash ≥ amount` 否则跳过（记 skips）
- 成交时真实扣款（按实算金额）；撤单/失效解冻
- 现金恒 ≥0 不变量在冻结语义下仍然成立（冻结额 ≤ 现金，单笔成交额 ≤ 冻结额 → 成交后 cash ≥ 0）

## 4. 卖出端修正（同批）

- `sell_check` 增加跌停判定：当前价 ≤ 跌停价 → 当日卖不出，跳过（持仓保留，次日再判定；止盈止损/到期规则次日继续有效）
- 跌停价 = 昨收 × (1 - 跌停幅度)（与 up_stop_price 对称的 down_stop_price，数据侧提供）
- 披露：跌停最终可能多日卖不出（真实场景），持仓天数口径不变（到期按自然日，结算日未卖出顺延下一交易日——既有到期逻辑已支持）

## 5. 数据接口（daemon 注入）

`paper_daemon` 新增 `tick_fn(codes) -> dict`：一次调用返回 `{code: {"last", "volume"(当日累计手), "bid_vol1", "bid1", "up_stop"(涨停价)}}` —— 由现有 provider 的 `get_full_tick` 封装（已连接 QMT，零新依赖）；全市场选股时点仍走既有 run_screen。每分钟结算边界与既有 SCREEN_TIMES 一致。

- `volume` 口径：`get_full_tick` 的 volume 为当日累计成交量（手）——与 `base_volume` 同源同口径
- 涨停价：provider 已提供 `up_stop_price`（选股用）；涨停判定 `last >= up_stop_price`（简化：等于即可，real-world 涨停价即 up_stop_price）

## 6. 账本版本与兼容

- state 增 `pending_buys: []`、`canceled_pending_codes: []`（当日）、`_version: 2`（新增键，非破坏）
- load 兼容：absent 键 → 缺省 `[]`；**既有账本（用户 100 万实账）零迁移成本平滑加载**
- `summary` 增 `pending_count`；`detail` 增 `pending` 区（网页"排队中"栏）

## 7. GUI 变更（最小）

- 模拟盘 tab：持仓表上方加"排队中"区（code/名称/委托价/股数/前方封单/已排队时长）——只读展示，复用既有渲染模式
- 逐笔流水自动展示 queue_cancel_break/queue_expire 条目（既有 trades 渲染不区分 reason，追加自然可见——需核对 reason 值不破坏现有筛选）

## 8. 安全边界（在既有 8 条之上追加）

1. 本升级零新增写端点（GUI 只读不变）
2. 排板判定数据全部来自**读** QMT 行情（get_full_tick），不写 QMT_SIGNALS、无下单调用
3. 冻结/解冻/成交三态全部原子保存，崩溃恢复不重复成交（幂等键分离）
4. pending 数据量上界：最多同时 5 持仓对应 ≤5 个 pending + 当日撤单记录（清理键在日切换时重置）

## 9. 简化披露（交付时向用户说明）

- 队列模型用"累计成交量穿越"代理真实排队（真实还有同价买盘竞争与撤单噪声——本模型**偏保守**，可接受且方向正确）
- 封单默认 2000 万门槛为经验值，可后续按策略调整（策略参数不暴露，需改代码阈值并披露）
- 成交整单而非部分成交（真实可能部分成交——简化，偏保守）
- 涨停判定取 last==up_stop（含盘中瞬时触板即算封板——真实需连续封板时长判定；简化）
- 尾盘 14:30 判定用委托时点的 up_stop 与触板时间（触板时间取当日首次 last 触及 up_stop 的时刻——tick_fn 需回传触板时间戳？**简化**：前置检查改为"委托时点 last 已 = up_stop 且 时间 < 14:30"——候选来自涨停池（已涨停）→ 触板时间不可得，用"时点筛选内已封板 + 时点<14:30"近似。披露）

## 10. 测试计划

- 状态机单元测试（tmp 账本注入）：
  - 成交：ΔV 穿越且封板 → 成交、扣款、进持仓、解冻差、pending 移除
  - 不成交：ΔV 不足 / 封单减少但 ΔV 不足 → 保持 pending
  - 开板撤单：last < 涨停价 → 撤单、解冻、未成交流水、当日 code 禁排
  - 收盘失效：结算时 pending → 清除+解冻+expire 流水
  - 冻结：两笔 pending 冻结互斥（现金不足跳过）；成交后 cash ≥ 0 不变量
  - 幂等：pending 存在不重复建；撤单后当日不再排
  - 迁移：旧账本（无 pending_buys）load → 平滑缺省
- 卖出端：跌停日 sell_check 跳过、次日恢复可卖
- daemon：tick_fn 注入的轮询判定集成测试；跨日启动清理
- GUI：DOM 冒烟（排队区标记）；detail/summary 字段测试
- 回归：既有 401 测试全绿（账本键新增不破坏既有断言）

## 11. 验收（用户在场）

1. 开盘时点：网页"排队中"出现真实委托（前方封单可见）
2. 当日至少一次"未成交（开板/收盘失效）"流水——真实打板第一课
3. 成交的票净值/持仓正常、费用口径正确
4. 模拟盘数字系统性低于旧版（预期，方向为真）
